\begin{abstract}
In the world of distributed systems, ensuring consistent replication among machines is crucial to achieve better performance, scalability and fault tolerance, this replication is also known as state machine replication (SMR). There are multiple ways to solve SMR, in this report will be discussing an ABD based SMR implementation and Multi-Paxos. The goal of the report is to explore each of these approaches, point out their benefits and drawbacks. Identifying these tradeoffs is crucial for the development of robust and efficient systems that are adequate to solve a specific problem.
\end{abstract}

\section{Introduction}
\label{sec:intro}
As demonstrated by FLP\cite{FLP} solution, achieving distributed consensus in a asynchronous environment with one faulty process is impossible, however, we can relax some properties of the consensus problem in order to have distributed consensus that works most of the times. In this report will be exploring different ways to relax the termination property of distributed consensus in order to have a practical consistent state replicated system across nodes using an ABD\cite{abd} based state machine protocol and Multi-Paxos\cite{multipaxos}.
\par The state replication described in this report consists of a replicated key-value map and the membership of the system, the goal of this project is to ensure consistent replication of these states across each replica\footnote{A replica is a node participating in the quorum decisions of the system}, so that a client requesting an read/write operation will be able to ensure that his write requests are atomically replicated in the system and that his read request will always return the last value updated in the system.
\par Multi-Paxos is a state machine replication protocol that admits and handles crash failures automatically, ABD by itself is just a quorum based system that guarantees atomic read-writes operations on a single registry, in order to implement state machine replication, some changes are needed.
\par The implementation of these protocols will be done in Java using the Babel Framework\cite{babelfmwk}.

\section{Related Work}
\subsection{Babel Framework}
\label{sec:BabelFramework}
The Babel framework is a Java-based framework developed in the NOVA LINCS (Nova Laboratory for Computer Science and Informatics)\cite{novaLincs}, designed to simplify the development of distributed, fault-tolerant, high-performance protocols. It abstracts the low-level complexities such as the communication management timeouts, and concurrency, allowing developers to focus on core protocol logic. Babel uses an event-driver model where protocols are implement as independent event-based state machines that process timers, messages and requests, and emit notifications.
\par In this report, the protocols were implemented using this framework, the nomenclature for the Pseudocode and explanations are in accordance with be the ones used in its respective paper.

\subsection{Multi-Paxos}
\label{sec:MultiPaxos}
In the paper "Paxos Made Simple"(implicitly describing Multi-Paxos as an optimization), Leslie Lamport explores how to optimize the Paxos consensus protocol for practical state machine replication. The protocol became widely recognized after its implementation by major companies like Google, and has since become a cornerstone for building fault-tolerant distributed systems, being particularly efficient for maintaining consistent state across multiple replicas.

The key insight of Multi-Paxos is that in a sequence of consensus decisions, such as in state machine replication, it's inefficient to run the complete Paxos protocol for each decision. Instead, after a leader is elected, subsequent consensus decisions can skip the prepare phase, reducing the message exchanges from 4 to 2 rounds. This optimization proves especially valuable in geo-distributed settings where network latency is significant.

The protocol divides consensus into ordered slots, where each slot represents one decision in the sequence. While a leader remains stable, it can propose values directly for consecutive slots using only the accept phase of Paxos. If the leader fails or becomes unreachable, a new leader is elected through a complete Paxos instance, ensuring all previously accepted values are preserved before resuming normal operation.

Multi-Paxos can be enhanced to handle membership changes automatically by treating them as special values that must be agreed upon through the consensus sequence. The protocol ensures that membership changes are totally ordered with respect to other operations, maintaining consistency even as the set of participating replicas evolves. These mechanics will be detailed in the Implementation(3.1) section of this report.


\subsection{ABD}
\label{sec:ABD}
In the paper "Sharing Memory Robustly in Message-Passing Systems"\cite{abd} (also known as ABD - H. Attiya, A. Bar-Noy, D. Dolev), the authors explore the implementation of shared memory in message-passing systems, by presenting emulators that translate shared-memory algorithms to message-passing models, implementing wait-free, atomic, single-writer multi-reader registers in unreliable, asynchronous networks. This approach takes advantages of quorum based systems in order to achieve replication of a single register, it does so by ensuring that every write is propagated through the system, and that every read returns the most recent value in the system. 
\par It's easily adapted to multiple registers, by running several instances of ABD in parallel identified by a key, additionally we can also run instances of ABD to automatically manage the membership of the system.
\par By changing the original protocol to account for multiple registers and handle membership change, we can achieve a SMR similar to Multi-Paxos(\ref{sec:MultiPaxos}), where membership is automatically managed via a series o mechanisms. These mechanisms will be expanded in the Implementation(\ref{sec:ABDImpl}) section of this report

\section{Implementation}
\subsection{Multi-Paxos based SMR}
The implementation consists of two main components: a \textbf{State Machine Replication (SMR)} protocol and an \textbf{Agreement} protocol based on Multi-Paxos.
The SMR protocol manages the replicated key-value store state and receives operation requests from HashApp or operation messages from other nodes, while the Agreement protocol ensures consistent ordering of operations across replicas through consensus.
The system assumes that before reaching a minimum quorum (3 replicas), the first node will be the leader and any new node join request will be immediately decided by the leader without running consensus. After reaching the minimum quorum size, the SMR protocol relies on the leader to order operations, which are then committed through Multi-Paxos consensus to ensure all replicas execute operations in the same order.
A heartbeat mechanism is used to detect leader failures, triggering leader election when necessary through the Agreement protocol.

\subsubsection{Leader Election}
The leader election mechanism in our Multi-Paxos implementation is built around a heartbeat-based failure detection system. The protocol maintains two main timers: a leader monitoring timer that runs on follower nodes and a heartbeat sending timer that runs on the leader node.

Leader nodes are configured to send heartbeat messages every \texttt{LEADER\_TIMEOUT/2} milliseconds (where \texttt{LEADER\_TIMEOUT} is set to 5000ms in the implementation). This is done through a periodic timer that triggers a heartbeat message to be sent to all other replicas in the membership:

\begin{algorithm}[H]
\begin{algorithmic}
\If{isLeader}
    \State heartbeatMessage $\leftarrow$ new HeartbeatMessage()
    \ForAll{host $\in$ membership}
        \If{!host.equals(self)}
            \State sendMessage(heartbeatMessage, host)
        \EndIf
    \EndFor
\EndIf
\end{algorithmic}
\end{algorithm}

Follower nodes maintain a boolean flag \texttt{receivedHeartbeat} that is set to true whenever they receive a heartbeat message from the current leader. A periodic timer running every \texttt{LEADER\_TIMEOUT} milliseconds checks this flag. If no heartbeat was received during this period, the follower initiates a leader election by starting a new instance of Paxos consensus with a special leader election operation:

\begin{algorithm}[H]
\begin{algorithmic}
\If{!isLeader \textbf{ and } !receivedHeartbeat}
    \State startLeaderElection()
    \State // Create new Paxos instance for leader election
    \State // Propose self as the new leader
\EndIf
\State receivedHeartbeat $\leftarrow$ false
\end{algorithmic}
\end{algorithm}

The leader election itself is conducted through a complete Paxos instance, where the proposed value is the identity of the new leader. This ensures all replicas agree on the new leader even in the presence of multiple concurrent leader elections. 

When the Agreement protocol completes the Paxos consensus for leader election, each node's Agreement protocol will notify its local SMR protocol through a \texttt{LeaderDecidedNotification}. This notification triggers the following state changes in the SMR protocol:

\begin{itemize}
\item If the local node is the new leader, sets its \texttt{isLeader} flag to true and starts the heartbeat timer
\item Updates its \texttt{currentLeader} reference
\item If not the leader, establishes a connection to the new leader
\end{itemize}

By using Paxos consensus for leader election, the system ensures that even with multiple nodes detecting leader failure simultaneously and proposing themselves as leaders, only one leader will be elected and acknowledged by all functioning replicas in the system.

\subsubsection{Membership Management}
The membership management in our implementation is responsible for handling new nodes joining the system and maintaining a consistent view of the active replicas across all nodes. The system maintains a \texttt{LinkedList<Host>} to track current members, where each \texttt{Host} represents a replica's network address and port.

When a new node wants to join the system, it sends a join request to its contact node. The behavior for processing this request varies depending on whether the system has reached minimum quorum (3 replicas):

Before minimum quorum:
\begin{itemize}
\item The leader can immediately accept new nodes without running consensus
\item The leader updates its membership list and sends a \texttt{StateTransferMessage} to the joining node
\item The joining node becomes ready to participate after processing the \texttt{StateTransferMessage}
\end{itemize}

After minimum quorum:
\begin{itemize}
\item The contact node forwards the join request to the current leader
\item The leader creates a special join operation and initiates a Paxos instance
\item Upon consensus completion, the leader sends a \texttt{StateTransferMessage} to the joining node
\item The joining node becomes ready to participate after processing the \texttt{StateTransferMessage}
\end{itemize}

The \texttt{StateTransferMessage} contains the current membership list and the system state. When a node receives this message, it updates its local state and becomes ready to participate in the system:

\begin{algorithm}[H]
\begin{algorithmic}
\Upon{ReceivedStateTransferMessage(msg, host)}
   \If{!msg.getLeader().equals(self)}
       \State this.membership $\leftarrow$ msg.getMembership()
       \State this.applicationState $\leftarrow$ deserializeState(msg.getState())
       \State this.readyOperationInstance $\leftarrow$ true
   \EndIf
\EndUpon
\end{algorithmic}
\end{algorithm}

Each membership change is treated as a special operation that must be processed before any subsequent operations can be executed, ensuring consistency in the membership view across all replicas.


\subsubsection{Consensus Implementation}
The consensus implementation in our Multi-Paxos based system is handled by the Agreement protocol, which ensures all replicas agree on the ordering and execution of operations. The protocol follows the standard Multi-Paxos flow but incorporates special handling for both regular operations and membership changes.
The core consensus logic is implemented through several key phases:
\begin{itemize}
\item \textbf{Prepare Phase}: When a proposer wants to propose a value, it first sends a PrepareMessage with a ballot number to all acceptors. The implementation handles this through the \texttt{uponPreparePaxosMessage} handler:
\begin{algorithm}[H]
\begin{algorithmic}
\If{ballot >= paxosInstance.getBallot()}
\State paxosInstance.setBallot(ballot)
\State paxosInstance.setPromise(host, true)
\State // Send Promise message back to proposer
\EndIf
\end{algorithmic}
\end{algorithm}
\item \textbf{Promise Phase}: Acceptors respond to prepare messages with promises, tracked in the \texttt{uponPromisePaxosMessage} handler. Once a quorum of promises is received, the proposer can move to the accept phase:
\begin{algorithm}[H]
\begin{algorithmic}
\If{hasQuorum(paxosInstance.getPromises())}
\State AcceptPaxosMessage acceptMsg = new AcceptPaxosMessage(
\State \hspace{1em}paxosInstance.getId(),
\State \hspace{1em}paxosInstance.getBallot(),
\State \hspace{1em}msg.getOperationID())
\State // Send Accept message to all replicas
\EndIf
\end{algorithmic}
\end{algorithm}
\item \textbf{Accept Phase}: The proposer sends accept messages with the proposed value. Acceptors validate the ballot number and respond with learn messages if they accept the proposal.
\item \textbf{Learn Phase}: Once a quorum of learn messages is received, the value is considered decided. The Agreement protocol notifies the SMR through specific notifications:
\begin{itemize}
\item \texttt{DecidedNotification}: For regular operations
\item \texttt{NodeDecidedNotification}: For membership changes
\item \texttt{LeaderDecidedNotification}: For leader changes
\end{itemize}
\end{itemize}
The implementation maintains all necessary state for each Paxos instance in a \texttt{PaxosInstance} class, which tracks:
\begin{itemize}
\item Ballot numbers
\item Promise and accept quorums
\item Instance type (REGULAR, JOIN, or LEADERELECTION)
\item Proposed values
\end{itemize}
When the Agreement protocol reaches consensus on an operation, it triggers the appropriate notification to the SMR protocol, which then executes the operation and updates its state.


\subsubsection{Operation Processing}
Operation processing in our Multi-Paxos based system begins when HashApp generates operation requests. These requests follow different paths depending on whether they are received by a leader or non-leader replica.
When a replica receives an OrderRequest from HashApp, it first checks if it's ready to process operations and if the operation hasn't been previously decided:
\begin{algorithm}[H]
\begin{algorithmic}
\If{!readyOperationInstance}
\State return
\EndIf
\If{decidedOperations.contains(request.getOpId())}
\State return
\EndIf
\end{algorithmic}
\end{algorithm}
If the replica is not the leader, it forwards the operation to the current leader via an OperationMessage:
\begin{algorithm}[H]
\begin{algorithmic}
\If{!isLeader}
\State OperationMessage msg = new OperationMessage(
\State \hspace{1em}request.getOpId(), self,
\State \hspace{1em}nextOperationInstance++,
\State \hspace{1em}request.getOperation())
\State openConnection(currentLeader)
\State sendMessage(msg, currentLeader)
\State return
\EndIf
\end{algorithmic}
\end{algorithm}
If the replica is the leader, it proposes the operation through the Agreement protocol:
\begin{algorithm}[H]
\begin{algorithmic}
\State ProposeRequest proposeRequest = new ProposeRequest(
\State \hspace{1em}nextOperationInstance++,
\State \hspace{1em}request.getOpId(),
\State \hspace{1em}request.getOperation())
\State sendRequest(proposeRequest, Agreement.PROTOCOLID)
\end{algorithmic}
\end{algorithm}
When an operation is decided, the Agreement protocol notifies the SMR through a DecidedNotification. Upon receiving this notification, the SMR:

Verifies the operation hasn't been already decided
Increments the next operation instance number
Updates its membership list
Executes the operation if there is payload
Records the operation as decided

In case of leadership changes, operations in progress may need to be restarted under the new leader. The system ensures safety by tracking decided operations to prevent duplicate execution.

\subsubsection{Limitation and Future Work}
Our current implementation, while functional, has several areas for potential improvement:
\textbf{Operation Recovery After Leadership Change}
Currently, when a new leader is elected, pending operations at the old leader are lost. A more robust implementation would include a mechanism to transfer pending operations to the new leader. This could be achieved by having replicas resend their pending operations to the new leader after receiving a LeaderDecidedNotification.
\textbf{Automatic Failure Detection and Cleanup}
While our implementation handles leader failure through the heartbeat mechanism, it lacks automatic cleanup of crashed replicas from the membership. Implementing this would require:
\begin{itemize}
\item A failure detection mechanism similar to the leader heartbeat
\item A consensus round to remove failed replicas
\item State cleanup for removed replicas
\end{itemize}
\textbf{Operation Processing Optimization}
Our current implementation handles operation requests and their execution in the same thread/context - when a request arrives, the handler both processes the request and, if appropriate, executes the propose operation immediately. We attempted to separate these concerns by having request handlers only validate the request and add it to a pendingOperations queue, with a separate periodic timer responsible for processing this queue and executing the propose operations. However, this approach resulted in significant performance degradation compared to the immediate execution model, leading us to maintain the coupled implementation. The cause of this performance issue with the decoupled approach warrants further investigation.
\textbf{Code and Data Structure Optimization}
The current implementation has several redundant data structures and classes that could be consolidated:
\begin{itemize}
\item Merge similar message types (PaxosMessage variants)
\item Unify notification structures across protocols
\item Reduce code duplication in message handlers
\item Simplify state tracking across Agreement and SMR protocols
\end{itemize}
\textbf{Additional Improvements}
Several other enhancements could be made to the system:
\begin{itemize}
\item Implement state transfer optimization to reduce the cost of bringing new replicas up-to-date
\item Add mechanisms to prevent unbounded growth of operation history
\item Implement snapshotting for faster recovery
\item Optimize the communication patterns between replicas
\end{itemize}


\subsection{ABD based SMR}
\label{sec:ABDImpl}
The implementation of state machine replication using quorums is essentially multiple ABD instances running in parallel with different objectives guaranteeing serialisability of each individual key or each membership change in the system. These objectives are defined in our implementation as \textbf{Operations} (Read Write Operation and Membership Operation). This implementation also assumes that the system always starts with three initial replicas (initial membership), but can handle memberships joining afterwards or leaving. Additionally, the system works as intended as long as three replicas remain in it. 
\subsubsection{Initialization}
\label{sec:initABD}
Upon starting, each replica starts initializes it's own state, that consists of:
\begin{itemize}
\setlength\itemsep{0em}
  \item \verb|membership|: Used to maintain the current membership of the system
  \item \verb|currentlyAlive|, \verb|pendingMembership|, \verb|membershipTag|: Helper data structures for maintaining the membership of the system. (See \ref{sec:abdmenb}).
  \item \verb|val|: Holds the key-value map to be replicated.
  \item \verb|tag|: A key-value map that holds the tag associated with each key (See \ref{sec:abdrw})
  \item \verb|inProgressOperations|: Holds the set operations that are currently in progress at a given instance.
  \item \verb|pendingOperations|: A Queue that stores operations received by the application, but are yet to be executed.
  \item \verb|opSeq|: Holds the current number of operations of this process.
\end{itemize}
\par If a replica integrates the initial membership of the system, it just adds the other replicas to the the membership, becomes automatically ready execute any request made by either the application or other replicas. Otherwise, it joins by requesting to a contact to join the system, then, it has to wait until it's integrated to start participating in the quorum.

\subsubsection{Operations Queues}
\label{sec:operatioQ}
The Operation object serves as a wrapper for each individual request. It's defined as an abstract class, implemented by the \verb|ReadWriteOperation| class and the \verb|MembershipOperation| class. The \verb|ReadWriteOperation| class can hold any Read or Write request made by the application, and the \verb|MembershipOperation| class can hold a membership change requested by a replica. When receiving these requests, they are placed in the \verb|pendingOperations| queue. This queue is then accessed repeatedly, with a predefined interval by a timer method event that processes the first operation in the queue and execute it's respective request. In order to avoid having multiple operations (in the same replica) executing for the same key, \verb|inProgressOperations| holds the operations that are currently waiting to terminate.
\par Effectively, we can have has many concurrent Read/Write operations as there are keys, however, to avoid overloading the CPU, we've created a mechanism that limits the amount of concurrent operations, by checking the current size of the \verb|inProgressOperations| set.

\subsubsection{Read Write Operations}
\label{sec:abdrw}
Read Write operations follow the pseudo code(TODO - link to pseudo code) presented.
\par \textbf{Write Operation}: The replica that receives the Write request (replica one), issues a request to all the other replicas to read the tag associated with a specific key, if the key is yet to be seen by any of the other replicas, it returns tag with a negative value. Replica one, upon reaching a quorum size of responses from the tags requested, it gets the maximum value from those tags, increments it, and sends a message to the other replicas to update their value and the tag associated with that key. The other replicas, when receiving this message, return an ack. Replica one, upon receiving these Acks and reaching a quorum, notifies the application that the write was complete.
\par \textbf{Read Operations}: The replica that receives the Read request for a specific key (replica one), requests a read for that key from all the other replicas in the system, from which they send the value and it's respective tag. When replica one receives a quorum size of responses, selects the value with the higher tag and, sends a write request to the other replicas, ensuring that this value is propagated. Upon receiving the write request for the new value, these replicas update their state, and return an Ack. Replica one, upon receiving enough Acks to build a quorum, notifies the application that the read operation was complete and returns the most up to date value.

\subsubsection{Membership Management}
\label{sec:abdmenb}
The Membership Management consists of either a replica joining or leaving the system. In contrast with the Read and Write requests, these requests are received from other replicas that detect changes in the membership, and they're all placed in the first position of the queue, additionally, they only start executing when there are no read or write requests in progress.
\par \textbf{Joining the system}: When a replica is trying to join the system (replica two), it sends a Join Request to it's contact (replica one), that adds a request to add a new replica to the first position of the \verb|pendingOperations| queue. Replica one, upon starting the operation, it sends a message for other replicas to send their membership tags, upon receiving enough replies to make a quorum, replica one gets the biggest tag, increments it, and sends it alongside with the replica to be added to the membership. The other replicas, upon receiving the information of the new replica, place it in the \verb|pendingMembership| set, and return an Ack to replica one. When replica one has enough Acks to make a quorum, sends a message with the current membership information to replica two, that upon receiving that information, set it's \verb|ready| state to true, sends a message to all the replicas in the membership, which in turn, remove this replica from the \verb|pendingMembership| set and add it to the \verb|membership| set. Replica two is now ready to start participating in the quorum. Since reads and writes are propagated, there's no need to share state, because the replicas will always quorum and propagate the most recent value.
\par \textbf{Leaving the System}:  Each replica periodically triggers a timer, configurable to a specific interval, that checks on all the other replicas. It does so, by sending a ping to every replica, then adds every replica that responds to the \verb|currentlyAlive|. When the timer triggers again, it checks if there are any replicas from the \verb|membership| set missing in the \verb|currentlyAlive| set, if so, adds the operation to remove the missing replicas to the first position of the \verb|pendingOperations| queue.
\par The execution of this operation is the mostly the same from the operation of adding a new replica, however, when the other replicas receive the information to remove the replica, the replica gets removed immediately and an ack is sent. The replica who requested the Remove operation, waits for a quorum (already with one less element) and removes the replica as well.
\par The implementation of this membership management protocol is, effectively, a an ABD write operation.

    \caption{Key-Value Store Replication Using Majority Quorums (Write \& Read)}
    \begin{algorithmic}
    
    \State \textbf{Upon write}(k, v) \textbf{do}:
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} $pending \leftarrow v$
    \State \hspace{3em} $opSeq \leftarrow opSeq + 1$
    \State \hspace{3em} $answers \leftarrow \{\}$
    \State \hspace{3em} Trigger bebBcastSend($\langle$READ-TAG, $opSeq$, $k$$\rangle$)
    \State

    \State \textbf{Upon bebBcastDeliver(READ-TAG, $id$, $k$ $\rangle$, $p$) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{Send}(\textsc{Read-Tag-Reply}, $p$, $id$, $tag[k]$)
    \State

    \State \textbf{Upon Receive($\langle$ READ-TAG-REPLY, $id$, $tag$$\rangle$, $p$ ) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{If} $opSeq = id$ \textbf{Then}
    \State \hspace{5em} $answers \leftarrow answers \cup \{\langle$ \textsc{Read-Tag-Reply}, $id$, $tag$ $\rangle\}$
    \State \hspace{5em} \textbf{If} $|answers| = \frac{\#\Pi+1}{2} + 1$ \textbf{Then}
    \State \hspace{6em} $new\text{-}tag \leftarrow$ \texttt{maxSQTag}($answers$)
    \State \hspace{6em} $opSeq \leftarrow opSeq + 1$
    \State \hspace{6em} $answers \leftarrow \{\}$
    \State \hspace{6em} \textbf{Trigger} bebBcastSend($\langle$ \textsc{Write}, $opSeq$, $k$, $\langle new\text{-}tag + 1$, $myself \rangle$, $pending$ $\rangle$)
    \State \hspace{6em} $pending \leftarrow \perp$
    \State
    
    \State \textbf{Upon bebBcastDeliver($\langle$ WRITE, $id$, $k$, $new\text{-}tag$, $v$ $\rangle$, $p$) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{If} $new\text{-}tag > tag[k]$ \textbf{Then}
    \State \hspace{5em} $tag[k] \leftarrow new\text{-}tag$
    \State \hspace{5em} $val[k] \leftarrow v$
    \State \hspace{3em} \textbf{Send}(\textsc{Ack}, $p$, $id$, $k$)
    \State
    
    \State \textbf{Upon Receive(\textsc{Ack}, $p$, $id$, $k$) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{If} $opSeq = id$ \textbf{Then}
    \State \hspace{4em} $answers \leftarrow answers \cup \{\langle$ \textsc{Ack}, $id$ $\rangle\}$
    \State \hspace{4em} \textbf{If} $|answers| = \frac{N+1}{2} + 1$ \textbf{Then}
    \State \hspace{5em} $answers \leftarrow \{\}$
    \State \hspace{5em} \textbf{If} $pending = \perp$ \textbf{Then}
    \State \hspace{6em} \textbf{Trigger WriteOK}($k$)
    \State \hspace{5em} \textbf{Else:}
    \State \hspace{6em} \textbf{Trigger ReadOK}($k$, \textbf{$pending$})
    \State

    \State \textbf{Upon read}($k$) \textbf{do}:
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} $opSeq \leftarrow opSeq + 1$
    \State \hspace{3em} $answers \leftarrow \{\}$
    \State \hspace{3em} \textbf{Trigger} bebBcastSend($\langle$\textsc{Read}, $opSeq$, $k$$\rangle$)
    \State

    \State \textbf{Upon bebBcastDeliver ($\langle$\textsc{Read}, $id$, $k$$\rangle$, $p$) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{Send}(\textsc{Read-Reply}, $p$, $id$, $k$, $tag[k]$, $val[k]$)
    \State

    \State \textbf{Upon Receive($\langle$\textsc{Read-Reply}, $id$, $k$, $tag$, $v$$\rangle$, $p$) do:}
    \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
    \State \hspace{3em} \textbf{If} $opSeq = id$ \textbf{Then}
    \State \hspace{4em} $answers \leftarrow answers \cup \{\langle$\textsc{Read-Reply}, $id$, $k$, $tag$, $v$$\rangle\}$
    \State \hspace{4em} \textbf{If} $|answers| = \frac{\#\Pi}{2} + 1$ \textbf{Then}
    \State \hspace{5em} $tag \leftarrow$ \texttt{maxTag}($answers$)
    \State \hspace{5em} $pending \leftarrow$ \texttt{valueOfMaxTag}($answers$)
    \State \hspace{5em} $opSeq \leftarrow opSeq + 1$
    \State \hspace{5em} $answers \leftarrow \{\}$
    \State \hspace{5em} \textbf{Trigger} bebBcastSend($\langle$\textsc{Write}, $opSeq$, $k$, $tag$, $pending$$\rangle$)
    \end{algorithmic}
  \end{algorithm}
  
\begin{algorithm}
    \caption{Membership Management - State, Init() \& Timer}
    \begin{algorithmic}
        \State \textbf{Interface:}
        \State \hspace{1em} \textbf{Requests:}
        \State \hspace{2em} \texttt{ChangeMembership}( $r$ , ACTION) //{where $r$ is the replica identifier and ACTION = \{ADD, REMOVE\}}
        \State
        \State \textbf{State:}
        \State \hspace{1em} $replicas$ {set containing all replicas}
        \State \hspace{1em} $currentlyAlive$ {set containing replicas currently active between timers}
        \State \hspace{1em} $pendingMembership$ {replica waiting to join }
        \State \hspace{1em} $myself$ {unique index of this replica}
        \State \hspace{1em} $membershipTag$ {set with timestamps - pair (sequenceNumb, process)}
        \State \hspace{1em} $opSeq$ {unique sequence number for operations at this process}
        \State \hspace{1em} $answers$ {set containing reply messages}
        \State \hspace{1em} $pending$ {pending value to be written}
        \State \hspace{1em} $T$ {period between healthchecks}
        \State

        \State \textbf{Upon Init() do:}
        \State \hspace{1em} \textbf{If} \textsc{isInitialMembership()}:
        \State \hspace{3em} $replicas \leftarrow \Pi$
        \State \hspace{1em} \textbf{Else}:
        \State \hspace{3em} $replicas \leftarrow \bot$
        \State \hspace{1em} $currentlyAlive \leftarrow replicas$
        \State \hspace{1em} $myself \leftarrow \texttt{mySequence}(\text{replicas})$
        \State \hspace{1em} $tag \leftarrow \{\}$
        \State \hspace{1em} $val \leftarrow \{\}$
        \State \hspace{1em} $opSeq \leftarrow 0$
        \State \hspace{1em} $pending \leftarrow \perp$
        \State \hspace{1em} \textbf{Setup Periodic Timer} HealthCheck($T$)
        \State

        \State \textbf{Upon Timer } HealthCheck \textbf{ do:}
        \State \hspace{1em} \textbf{If} $\#replicas \neq \#currentlyAlive$ \textbf{Then}
        \State \hspace{3em} \textbf{Trigger} bebBcastSend(READ-TAG-MEMBERSHIP, $currentlyAlive, \langle opSeq, REMOVE\rangle$)
        \State \hspace{1em} \textbf{Else}
        \State \hspace{3em} \textbf{Trigger} bebBcastSend(Ping, $replicas$)
        \State \hspace{1em} $currentlyAlive \leftarrow \{\}$
        \State

        \State \textbf{Upon Ping}($p$) \textbf{do:}
        \State \hspace{3em} \textbf{Send}(Pong, $p$)
        \State
        

        \State \textbf{Upon Pong}($p$) \textbf{do:}
        \State \hspace{3em} $currentlyAlive \leftarrow currentlyAlive \cup p$
        \State
    \end{algorithmic}
\end{algorithm}

\begin{algorithm}
    \caption{Membership Management - Join \& Remove}
    \begin{algorithmic}        
        \State \textbf{Upon ChangeMembership}(r, ADD) \textbf{do:}
        \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
        \State \hspace{3em} $pending \leftarrow r$
        \State \hspace{3em} $pendingMembership \leftarrow r$
        \State \hspace{3em} $opSeq \leftarrow opSeq + 1$
        \State \hspace{3em} $answers \leftarrow \{\}$
        \State \hspace{3em} Trigger bebBcastSend(READ-TAG-MEMBERSHIP, $replicas, \langle opSeq, ADD\rangle$)
        \State

        \State \textbf{Upon bebBcastDeliver(READ-TAG-MEMBERSHIP, $id$, ACTION$\rangle$, $p$) do:}
        \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
        \State \hspace{3em} \textbf{Send}(\textsc{Read-Tag-Reply-Membership}, $p$ $\langle id, membershipTag, ACTION\rangle$)
        \State

        \State \textbf{Upon Receive($\langle$ READ-TAG-REPLY-MEMBERSHIP, $id$, $membershipTag$$, ACTION\rangle$, $p$) do:}
        \State \hspace{1em} \textbf{If} \textsc{$pending \neq \bot$}:
        \State \hspace{3em} \textbf{If} $opSeq = id$ \textbf{Then}
        \State \hspace{4em} $answers \leftarrow answers \cup \{\langle$ \textsc{Read-Tag-Reply-Membership}, $id$, $tag$ $\rangle\}$
        \State \hspace{4em} \textbf{If} $|answers| = \frac{\#\Pi+1}{2} + 1$ \textbf{Then}
        \State \hspace{5em} $new\text{-}tag \leftarrow$ \texttt{maxSQTag}($answers$)
        \State \hspace{5em} $opSeq \leftarrow opSeq + 1$
        \State \hspace{5em} $answers \leftarrow \{\}$
        \State \hspace{5em} \textbf{Trigger} bebBcastSend(\textsc{WriteMembership}, $replicas \langle, opSeq$, $\langle new\text{-}tag + 1$, $myself \rangle$, $pending$, ACTION$\rangle$)
        \State \hspace{5em} $pending \leftarrow \perp$
        \State

        \State \textbf{Upon bebBcastDeliver($\langle$ WRITEMEMBERSHIP, $id$, $new\text{-}tag$, $r$, ACTION $\rangle$, $p$) do:}
        \State \hspace{1em} \textbf{If} $new\text{-}tag > tag$ \textbf{Then}
        \State \hspace{2em} \textbf{If} $ACTION = ADD$ \textbf{Then}
        \State \hspace{3em} $membershipTag \leftarrow new\text{-}tag$
        \State \hspace{3em} $pendingMembership \leftarrow r$
        \State \hspace{2em} \textbf{Else}
        \State \hspace{3em} $replicas \leftarrow replicas \setminus \{pendingMembership\}$
        \State \hspace{1em} \textbf{Send}($\langle$ \textsc{MembershipAck}, $p$, $id$ $\rangle$)
        \State

        \State \textbf{Upon Receive($\langle$ \textsc{MembershipAck}, $p$, $id$, ACTION $\rangle$) do:}
        \State \hspace{1em} \textbf{If} $opSeq = id$ \textbf{Then}
        \State \hspace{2em} $answers \leftarrow answers \cup \{\langle$ \textsc{Ack}, $id$ $\rangle\}$
        \State \hspace{2em} \textbf{If} $|answers| = \frac{N+1}{2} + 1$ \textbf{Then}
        \State \hspace{3em} $answers \leftarrow \{\}$
        \State \hspace{3em} \textbf{If} $pending = \perp$ \textbf{Then}
        \State \hspace{4em} \textbf{If} $ACTION = ADD$ \textbf{Then}
        \State \hspace{5em} \textbf{Send}($\langle$\textsc{JoinReply}, $pendingMembership$, $membershipTag$, $replicas$ $\rangle$)
        \State \hspace{4em} \textbf{Else}
        \State \hspace{5em} $replicas \leftarrow replicas \setminus \{pendingMembership\}$
        \State

        \State \textbf{Upon Receive($\langle$ \textsc{JoinReply}, $p$, $membershipTagReceived$, $replicasReceived$ $\rangle$) do:}
        \State \hspace{1em} $replicas \leftarrow replicasReceived$
        \State \hspace{1em} $membershipTag \leftarrow membershipTagReceived$
        \State \hspace{1em} \textbf{Trigger} bebBcastSend(\textsc{Joined}, $replicas, myself$)
        \State

        \State \textbf{Upon bebBcastDeliver($ \textsc{Joined}, p$) do:}
        \State \hspace{1em} $replicas \leftarrow replicas \cup \{p\}$
        \State \hspace{1em} $pendingMembership \leftarrow \bot$


    \end{algorithmic}
\end{algorithm}
