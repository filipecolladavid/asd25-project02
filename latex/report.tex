\begin{abstract}
	In the world of distributed systems, ensuring consistent replication among machines is crucial to achieve better performance, scalability and fault tolerance, this replication is also known as state machine replication (SMR). There are multiple ways to solve SMR, in this report will be discussing an ABD based SMR implementation and Multi-Paxos. The goal of the report is to explore each of these approaches, point out their benefits and drawbacks. Identifying these tradeoffs is crucial for the development of robust and efficient systems that are adequate to solve a specific problem.
\end{abstract}

\section{Introduction}
\label{sec:intro}
As demonstrated by FLP\cite{FLP} solution, achieving distributed consensus in a asynchronous environment with one faulty process is impossible, however, we can relax some properties of the consensus problem in order to have distributed consensus that works most of the times. In this report will be exploring different ways to relax the termination property of distributed consensus in order to have a practical consistent state replicated system across nodes using an ABD\cite{abd} based state machine protocol and Multi-Paxos\cite{multipaxos}.
\par The state replication described in this report consists of a replicated key-value map and the membership of the system, the goal of this project is to ensure consistent replication of these states across each replica\footnote{A replica is a node participating in the quorum decisions of the system}, so that a client requesting an read/write operation will be able to ensure that his write requests are atomically replicated in the system and that his read request will always return the last value updated in the system.
\par Multi-Paxos is a state machine replication protocol that admits and handles crash failures automatically, ABD by itself is just a quorum based system that guarantees atomic read-writes operations on a single registry, in order to implement state machine replication, some changes are needed.
\par The implementation of these protocols will be done in Java using the Babel Framework\cite{babelfmwk}.

\section{Related Work}
\subsection{Babel Framework}
\label{sec:BabelFramework}
The Babel framework is a Java-based framework developed in the NOVA LINCS (Nova Laboratory for Computer Science and Informatics)\cite{novaLincs}, designed to simplify the development of distributed, fault-tolerant, high-performance protocols. It abstracts the low-level complexities such as the communication management timeouts, and concurrency, allowing developers to focus on core protocol logic. Babel uses an event-driver model where protocols are implement as independent event-based state machines that process timers, messages and requests, and emit notifications.
\par In this report, the protocols were implemented using this framework, the nomenclature for the Pseudocode and explanations are in accordance with be the ones used in its respective paper.

\subsection{Multi-Paxos}
\label{sec:MultiPaxos}
In the paper "Paxos Made Simple"\cite{Lamport2001PaxosMS}(implicitly describing Multi-Paxos as an optimization), Leslie Lamport explores how to optimize the Paxos consensus protocol for practical state machine replication. The protocol became widely recognized after its implementation by major companies like Google, and has since become a cornerstone for building fault-tolerant distributed systems, being particularly efficient for maintaining consistent state across multiple replicas.

The key insight of Multi-Paxos is that in a sequence of consensus decisions, such as in state machine replication, it's inefficient to run the complete Paxos protocol for each decision. Instead, after a leader is elected, subsequent consensus decisions can skip the prepare phase, reducing the message exchanges from 4 to 2 rounds. This optimization proves especially valuable in geo-distributed settings where network latency is significant.

The protocol divides consensus into ordered slots, where each slot represents one decision in the sequence. While a leader remains stable, it can propose values directly for consecutive slots using only the accept phase of Paxos. If the leader fails or becomes unreachable, a new leader is elected through a complete Paxos instance, ensuring all previously accepted values are preserved before resuming normal operation.

Multi-Paxos can be enhanced to handle membership changes automatically by treating them as special values that must be agreed upon through the consensus sequence. The protocol ensures that membership changes are totally ordered with respect to other operations, maintaining consistency even as the set of participating replicas evolves. These mechanics will be detailed in the Implementation(3.1) section of this report.


\subsection{ABD}
\label{sec:ABD}
In the paper "Sharing Memory Robustly in Message-Passing Systems"\cite{abd} (also known as ABD - H. Attiya, A. Bar-Noy, D. Dolev), the authors explore the implementation of sharing memory in message-passing systems, by presenting emulators that translate shared-memory algorithms to message-passing models, implementing wait-free, atomic, single-writer multi-reader registers in unreliable, asynchronous networks. This approach takes advantages of quorum based systems in order to achieve replication of a single register, it does so by ensuring that every write is propagated through the system, and that every read returns the most recent value in the system.
\par It's easily adapted to multiple registers, by running several instances of ABD in parallel identified by a key, additionally we can also run instances of ABD to automatically manage the membership of the system.
\par By changing the original protocol to account for multiple registers and handle membership change, we can achieve a SMR similar to Multi-Paxos(\ref{sec:MultiPaxos}), where membership is automatically managed via a series o mechanisms. These mechanisms will be expanded in the Implementation(\ref{sec:ABDImpl}) section of this report

\section{Implementation}
\subsection{Multi-Paxos based SMR}
The implementation consists of two main components: a \textbf{State Machine Replication (SMR)} protocol and an \textbf{Agreement} protocol based on Multi-Paxos.
The SMR protocol manages the replicated key-value store state and receives operation requests from HashApp or operation messages from other nodes, while the Agreement protocol ensures consistent ordering of operations across replicas through consensus.
The system assumes that before reaching a minimum quorum (3 replicas), the first node will be the leader and any new node join request will be immediately decided by the leader without running consensus. After reaching the minimum quorum size, the SMR protocol relies on the leader to order operations, which are then committed through Multi-Paxos consensus to ensure all replicas execute operations in the same order.
A heartbeat mechanism is used to detect leader failures, triggering leader election when necessary through the Agreement protocol.

\subsubsection{Leader Election}
The leader election mechanism in our Multi-Paxos implementation is built around a heartbeat-based failure detection system. The protocol maintains two main timers: a leader monitoring timer that runs on follower nodes and a heartbeat sending timer that runs on the leader node.

Leader nodes are configured to send heartbeat messages every \texttt{LEADER\_TIMEOUT/2} milliseconds (where \texttt{LEADER\_TIMEOUT} is set to 5000ms in the implementation). This is done through a periodic timer that triggers a heartbeat message to be sent to all other replicas in the membership:

\begin{algorithm}[H]
	\begin{algorithmic}
		\If{isLeader}
		\State heartbeatMessage $\leftarrow$ new HeartbeatMessage()
		\ForAll{host $\in$ membership}
		\If{!host.equals(self)}
		\State sendMessage(heartbeatMessage, host)
		\EndIf
		\EndFor
		\EndIf
	\end{algorithmic}
\end{algorithm}

Follower nodes maintain a boolean flag \texttt{receivedHeartbeat} that is set to true whenever they receive a heartbeat message from the current leader. A periodic timer running every \texttt{LEADER\_TIMEOUT} milliseconds checks this flag. If no heartbeat was received during this period, the follower initiates a leader election by starting a new instance of Paxos consensus with a special leader election operation:

\begin{algorithm}[H]
	\begin{algorithmic}
		\If{!isLeader \textbf{ and } !receivedHeartbeat}
		\State startLeaderElection()
		\State // Create new Paxos instance for leader election
		\State // Propose self as the new leader
		\EndIf
		\State receivedHeartbeat $\leftarrow$ false
	\end{algorithmic}
\end{algorithm}

The leader election itself is conducted through a complete Paxos instance, where the proposed value is the identity of the new leader. This ensures all replicas agree on the new leader even in the presence of multiple concurrent leader elections.

When the Agreement protocol completes the Paxos consensus for leader election, each node's Agreement protocol will notify its local SMR protocol through a \texttt{LeaderDecidedNotification}. This notification triggers the following state changes in the SMR protocol:

\begin{itemize}
  	\setlength\itemsep{0em}
	\item If the local node is the new leader, sets its \texttt{isLeader} flag to true and starts the heartbeat timer
	\item Updates its \texttt{currentLeader} reference
	\item If not the leader, establishes a connection to the new leader
\end{itemize}

By using Paxos consensus for leader election, the system ensures that even with multiple nodes detecting leader failure simultaneously and proposing themselves as leaders, only one leader will be elected and acknowledged by all functioning replicas in the system.

\subsubsection{Membership Management}
The membership management in our implementation is responsible for handling new nodes joining the system and maintaining a consistent view of the active replicas across all nodes. The system maintains a \texttt{LinkedList<Host>} to track current members, where each \texttt{Host} represents a replica's network address and port.

When a new node wants to join the system, it sends a join request to its contact node. The behavior for processing this request varies depending on whether the system has reached minimum quorum (3 replicas):

Before minimum quorum:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item The leader can immediately accept new nodes without running consensus
	\item The leader updates its membership list and sends a \texttt{StateTransferMessage} to the joining node
	\item The joining node becomes ready to participate after processing the \texttt{StateTransferMessage}
\end{itemize}

After minimum quorum:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item The contact node forwards the join request to the current leader
	\item The leader creates a special join operation and initiates a Paxos instance
	\item Upon consensus completion, the leader sends a \texttt{StateTransferMessage} to the joining node
	\item The joining node becomes ready to participate after processing the \texttt{StateTransferMessage}
\end{itemize}

The \texttt{StateTransferMessage} contains the current membership list and the system state. When a node receives this message, it updates its local state and becomes ready to participate in the system:

\begin{algorithm}[H]
	\begin{algorithmic}
		\Upon{ReceivedStateTransferMessage(msg, host)}
		\If{!msg.getLeader().equals(self)}
		\State this.membership $\leftarrow$ msg.getMembership()
		\State this.applicationState $\leftarrow$ deserializeState(msg.getState())
		\State this.readyOperationInstance $\leftarrow$ true
		\EndIf
		\EndUpon
	\end{algorithmic}
\end{algorithm}

Each membership change is treated as a special operation that must be processed before any subsequent operations can be executed, ensuring consistency in the membership view across all replicas.


\subsubsection{Consensus Implementation}
The consensus implementation optimizes for the common case of a stable leader while maintaining safety during leader changes:

1. \textbf{Normal Operation (Stable Leader):}
   \begin{itemize}
    	\setlength\itemsep{0em}
   \item Leader skips Prepare phase and directly sends AcceptPaxosMessage to all replicas
   \item Acceptors respond with LearnPaxosMessage
   \item Decision reached after quorum of Learn messages
   \end{itemize}

2. \textbf{Leader Recovery:}
   \begin{itemize}
    	\setlength\itemsep{0em}
   \item New leader must start complete Paxos instance with Prepare phase
   \item Sends PrepareMessage with higher ballot number
   \item Collects Promise responses from quorum
   \item Proceeds with Accept phase after quorum reached
   \end{itemize}

3. \textbf{Decision Processing:}
   \begin{itemize}
    	\setlength\itemsep{0em}
   \item Upon receiving a quorum of accepts, processes decision based on operation type
   \item For leader election operations, updates leadership state and starts heartbeat if elected
   \item For join operations, updates membership list with new node
   \item For regular operations, triggers notification to SMR for execution 
   \item All decisions update internal state and clean up operation metadata
   \end{itemize}
The implementation maintains all necessary state for each Paxos instance in a \texttt{PaxosInstance} class, which tracks:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item Ballot numbers
	\item Promise and accept quorums
	\item Instance type (REGULAR, JOIN, or LEADERELECTION)
	\item Proposed values
\end{itemize}
When the Agreement protocol reaches consensus on an operation, it triggers the appropriate notification to the SMR protocol, which then executes the operation and updates its state.


\subsubsection{Operation Processing}
Operation processing in our Multi-Paxos based system begins when HashApp generates operation requests. These requests follow different paths depending on whether they are received by a leader or non-leader replica. When a replica receives an OrderRequest from HashApp, it first checks if it's ready to process operations and if the operation hasn't been previously decided:
If the replica is not the leader, it forwards the operation to the current leader via an OperationMessage:
\begin{algorithm}[H]
	\begin{algorithmic}
		\If{!isLeader}
		\State OperationMessage msg = new OperationMessage(
		\State \hspace{1em}request.getOpId(), self,
		\State \hspace{1em}nextOperationInstance++,
		\State \hspace{1em}request.getOperation())
		\State openConnection(currentLeader)
		\State sendMessage(msg, currentLeader)
		\State return
		\EndIf
	\end{algorithmic}
\end{algorithm}
If the replica is the leader, it proposes the operation through the Agreement protocol:
\begin{algorithm}[H]
	\begin{algorithmic}
		\State ProposeRequest proposeRequest = new ProposeRequest(
		\State \hspace{1em}nextOperationInstance++,
		\State \hspace{1em}request.getOpId(),
		\State \hspace{1em}request.getOperation())
		\State sendRequest(proposeRequest, Agreement.PROTOCOLID)
	\end{algorithmic}
\end{algorithm}
When an operation is decided, the Agreement protocol notifies the SMR through a DecidedNotification. Upon receiving this notification, the SMR:

Verifies the operation hasn't been already decided
Increments the next operation instance number
Updates its membership list
Executes the operation if there is payload
Records the operation as decided

In case of leadership changes, operations in progress may need to be restarted under the new leader. The system ensures safety by tracking decided operations to prevent duplicate execution.

\subsection{ABD based SMR}
\label{sec:ABDImpl}
The implementation of state machine replication using quorums is essentially multiple ABD instances running in parallel with different objectives guaranteeing serialisability of each individual key or each membership change in the system. These objectives are defined in our implementation as \textbf{Operations} (Read Write Operation and Membership Operation). This implementation also assumes that the system starts with, at least, three initial replicas (initial membership), but can handle memberships joining afterwards or leaving. Additionally, the system works as intended as long as three replicas remain in it.
\subsubsection{Initialization}
\label{sec:initABD}
The initialization of each ABD replica is described in the appendix \ref{code:ABDSMR}, Algorithm 1. Upon starting, each replica starts initializes it's own state, that consists of:
\begin{itemize}
	\setlength\itemsep{0em}
	\item \verb|membership|: An HashSet, used to maintain the current membership of the system
	\item \verb|currentlyAlive|, \verb|pendingMembership|, \verb|membershipTag|: Helper data structures (HashSets) for maintaining the membership of the system. (See \ref{sec:abdmenb}).
	\item \verb|val|: Holds a key-value map (HashMap) to be replicated.
	\item \verb|tag|: A key-value map that holds the tag associated with each key (See \ref{sec:abdrw})
	\item \verb|inProgressOperations|: Holds the set operations that are currently in progress at a given instance.
	\item \verb|pendingOperations|: A Queue that stores operations received by the application, but are yet to be executed.
	\item \verb|opSeq|: An HashSet that holds the current number of operations of this process.
\end{itemize}
\par If a replica integrates the initial membership of the system, it just adds the other replicas to the the membership, and updates it's \verb|ready| state to \verb|true|, meaning that it's immediately available to execute any request made by either the application or other replicas. Otherwise, it joins by requesting to a contact to join the system, then, it has to wait until it's integrated to start participating in the quorum. In the implementation we use a boolean to represent the \verb|ready| state of replica, however in the pseudocode this state is verified by checking weather the \verb|replicas| set was not initialized (is null or bottom).

\subsubsection{Operations Queues}
\label{sec:operatioQ}
The Operation object serves as a wrapper for each individual request. It's defined as an abstract class, implemented by the \verb|ReadWriteOperation| class and the \verb|MembershipOperation| class. The \verb|ReadWriteOperation| class represents any Read or Write request made by the application, and the \verb|MembershipOperation| class represents a membership change requested by a replica. When receiving these requests, they are placed in the \verb|pendingOperations| queue. This queue is then accessed repeatedly, with a predefined interval by a timer method event that processes the first operation in the queue and execute it's respective request.
\par In order to avoid having multiple operations (in the same replica) executing for the same key, \verb|inProgressOperations| holds the operations that are currently waiting to terminate. Upon starting an operation, the replica verifies if the \verb|inProgressOperations| hashset already contains an operation for that key, if so, it wait's until that operation is completed.
\par Effectively, we can have has many concurrent Read/Write operations as there are keys, however, to avoid overloading the CPU, we've created a mechanism that limits the amount of concurrent operations, by limiting the maximum size of the \verb|inProgressOperations| set.
\par The objects and methods described in this subsection are not represented in the pseudo code as they're not part of the algorithm itself, but an improvement to handle multiple concurrent requests on different replicas.

\subsubsection{Read Write Operations}
\label{sec:abdrw}
The description of these operations follows the pseudocode available in the appendix \ref{code:ABDSMRRW} Algorithm 2.
\par \textbf{Write Operation}: The replica that receives the Write request (replica one), issues a request to all the other replicas to read the tag associated with a specific key, if the key is yet to be seen by any of the other replicas, it returns tag with a negative value. Replica one, upon reaching a quorum size of responses from the tags requested, it gets the maximum value from those tags, increments it, and sends a message to the other replicas to update their value and the tag associated with that key. The other replicas, when receiving this message, return an ack. Replica one, upon receiving these Acks and reaching a quorum, notifies the application that the write was complete.
\par \textbf{Read Operations}: The replica that receives the Read request for a specific key (replica one), requests a read for that key from all the other replicas in the system, from which they send the value and it's respective tag. When replica one receives a quorum size of responses, selects the value with the higher tag and, sends a write request to the other replicas, ensuring that this value is propagated. Upon receiving the write request for the new value, the other replicas update their state, and return an Ack. Replica one, upon receiving enough Acks to build a quorum, notifies the application that the read operation was complete and returns the most up to date value.

\subsubsection{Membership Management}
\label{sec:abdmenb}
The Membership Management consists of either a replica joining or leaving the system. In contrast with the Read and Write requests, these requests are received from other replicas that detect changes in the membership, and they're all placed in the first position of the queue, additionally, they only start executing when there are no read or write requests in progress. The pseudo code for the Membership Management is described in the appendix \ref{code:ABDSMR}, Algorithm 3 and Algorithm 4.
\par \textbf{Joining the system}: When a replica is trying to join the system (replica two), it sends a Join Request to it's contact (replica one), that adds a request to add a new replica to the first position of the \verb|pendingOperations| queue. Replica one, upon starting the operation, it sends a message for other replicas to send their membership tags, upon receiving enough replies to make a quorum, replica one gets the biggest tag, increments it, and sends it alongside with the replica to be added to the membership. The other replicas, upon receiving the information of the new replica, place it in the \verb|pendingMembership| set, and return an Ack to replica one. When replica one has enough Acks to make a quorum, sends a message with the current membership information to replica two, that upon receiving that information, set it's \verb|ready| state to true, sends a message to all the replicas in the membership, which in turn, remove this replica from the \verb|pendingMembership| set and add it to the \verb|membership| set. Replica two is now ready to start participating in the quorum. Since reads and writes are propagated, there's no need to share state, because the replicas will always quorum and propagate the most recent value.
\par \textbf{Leaving the System}:  Each replica periodically triggers a timer, configurable to a specific interval, that checks on all the other replicas. It does so, by sending a ping to every replica, then adds every replica that responds to the \verb|currentlyAlive|. When the timer triggers again, it checks if there are any replicas from the \verb|membership| set missing in the \verb|currentlyAlive| set, if so, adds the operation to remove the missing replicas to the first position of the \verb|pendingOperations| queue.
\par The execution of this operation is the mostly the same from the operation of adding a new replica, however, when the other replicas receive the information to remove the replica, the replica gets removed immediately and an ack is sent. The replica who requested the Remove operation, waits for a quorum (already with one less element) and removes the replica as well.
\par The implementation of this membership management protocol is, effectively, a an ABD write operation.



\section{Experimentation and Results}
\label{sec:ExpResults}
The experimental evaluation was conducted in a distributed environment using four nodes, one as the client and three servers. The test scenario consisted of executing 5,000 operations with a balanced mix of reads and writes. We compared three different consensus protocols: basic Paxos, Multi-Paxos, and ABD (Attiya, Bar-Noy, Dolev). All tests were performed with consistent parameters including quorum size (2 out of 3 nodes) and network conditions. Additionally, for ABD, the timer that executes \verb|pendingOperations| was set to $5~\mu\text{s}$. The value of this interval changes drastically results of the operations, increasing sthe value leeds to higher response times, lowering increases the probability of synchronization issues (see Section \ref{sec:abdlimitfuture})
\subsubsection{Overall Throughput}

	\centering
	\includegraphics[width=0.45\textwidth]{figures/throughput.pdf}

The throughput analysis reveals significant performance differences among the protocols. Multi-Paxos and ABD demonstrate similar throughput capabilities (70.93 and 71.77 ops/sec respectively), both substantially outperforming basic Paxos (50.89 ops/sec). This performance gap can be attributed to the reduced message complexity in both Multi-Paxos and ABD compared to basic Paxos. The similarity between Multi-Paxos and ABD throughput suggests that both implementations of the protocols effectively optimize their communication patterns for sustained operation.

Latency measurements show distinct characteristics for each protocol. All protocols show some initial ramp-up period, with Multi-Paxos achieving optimal performance fastest.
\subsubsection{Summary}
The experimental results demonstrate that both Multi-Paxos and ABD offer significant improvements over basic Paxos, with Multi-Paxos showing slightly better overall characteristics for balanced workloads. ABD proves particularly efficient for write operations, making it a strong candidate for write-heavy workloads.

\section{Limitations and Future Work}
\label{sec:limitationsfuture}
\subsection{Paxos}
\label{sec:paxoslimitfuture}
Our current implementation, while functional, has several areas for potential improvement:
\par \textbf{Operation Recovery After Leadership Change}: Currently, when a new leader is elected, pending operations at the old leader are lost. A more robust implementation would include a mechanism to transfer pending operations to the new leader. This could be achieved by having replicas resend their pending operations to the new leader after receiving a LeaderDecidedNotification.
\par \textbf{Automatic Failure Detection and Cleanup}: While our implementation handles leader failure through the heartbeat mechanism, it lacks automatic cleanup of crashed replicas from the membership. Implementing this would require:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item A failure detection mechanism similar to the leader heartbeat
	\item A consensus round to remove failed replicas
	\item State cleanup for removed replicas
\end{itemize}
\par \textbf{Operation Processing Optimization}: Our current implementation handles operation requests and their execution in the same thread/context - when a request arrives, the handler both processes the request and, if appropriate, executes the propose operation immediately. We attempted to separate these concerns by having request handlers only validate the request and add it to a pendingOperations queue, with a separate periodic timer responsible for processing this queue and executing the propose operations. However, this approach resulted in significant performance degradation compared to the immediate execution model, leading us to maintain the coupled implementation. The cause of this performance issue with the decoupled approach warrants further investigation.
\par \textbf{Code and Data Structure Optimization}: The current implementation has several redundant data structures and classes that could be consolidated:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item Merge similar message types (PaxosMessage variants)
	\item Unify notification structures across protocols
	\item Reduce code duplication in message handlers
	\item Simplify state tracking across Agreement and SMR protocols
\end{itemize}
\par \textbf{Additional Improvements}: Several other enhancements could be made to the system:
\begin{itemize}
  	\setlength\itemsep{0em}
	\item Implement state transfer optimization to reduce the cost of bringing new replicas up-to-date
	\item Implement snapshotting for faster recovery
	\item Optimize the communication patterns between replicas
\end{itemize}
\subsection{ABD}
\label{sec:abdlimitfuture}
\textbf{Implementation Issues}: When testing the ABD implementation with heavier workloads, one of the replicas would stop replying to the application, however, as far as we tested, it would keep on participating in the quorum decisions. Additionally, we've noticed that disabling the logs and slightly increasing the interval from which pendingOperations would be executed would improve it's performance, which led us to believe that the underlying problem could some synchronization issue that would result in a memory race (even if we used Concurrent Data Structures).
\par \textbf{Timers}: In hindsight, the use of timers to execute pending operations creates multiple synchronization issues, as future work, trying an implementation that didn't relied on timers such as explicitly creating a thread for each request received.
\par \textbf{Membership Management}: We also noticed that when introducing automatic membership management, the system would struggle even more with additional workload. Since it was also implemented with a timer, we also believe that it could be some synchronization issue.
\par \textbf{Membership Algorithm}: The membership algorithm could be stronger, for instance when removing a replica, replicas other than the one proposing the removal, don't explicitly wait for a quorum to remove the unresponsive replica.


\section{Conclusion}
\label{conclusion}
In this project we've explored two different protocols to solve consensus, ABD and Multi-Paxos
\par The ABD protocol is a much simpler solution for consensus, that enforces serialisability for each individual key, and further adaptations are required to handle membership changes.
\par Multi-Paxos protocol demo nstrates the practical viability of achieving consistent replication in distributed systems while ensuring linearisabiliy of operations. The system's architecture, divided into an Agreement protocol for consensus and a State Machine protocol for state management, effectively handles both normal operations and membership changes while maintaining consistency.
\par The experimental evaluation revealed several key insights about these consensus protocols:
\begin{itemize}
\setlength\itemsep{0em}
\item Multi-Paxos significantly outperforms basic Paxos by reducing message complexity when a stable leader exists, improving overall system throughput by approximately 40%
\item Message efficiency is substantially improved in Multi-Paxos, requiring only 2 messages per operation after leader election compared to 4 messages in basic Paxos
\item While ABD showed excellent write performance, Multi-Paxos demonstrated better balance between read and write operations, making it more suitable for mixed workloads
\end{itemize}

\begin{algorithm}
\caption{Multi-Paxos Agreement Protocol}
\begin{algorithmic}
\State \textbf{State:}
\State \hspace{1em} $self$ {identity of this node}
\State \hspace{1em} $membership$ {list of nodes in the system}
\State \hspace{1em} $currentLeader$ {current leader node}
\State \hspace{1em} $isLeader$ {boolean indicating if this node is leader}
\State \hspace{1em} $listOfProposes$ {map of UUID to PaxosInstance}
\State \hspace{1em} $decidedMessages$ {map of UUID to LearnMessage}
\State

\State \textbf{Upon proposeRequest}($instance$, $opId$, $operation$) \textbf{do:}
\If{$opId \in listOfProposes$}
\State \Return
\EndIf
\If{$\neg isLeader$}
\State $msg \leftarrow$ new OperationMessage($opId$, $self$, $instance$, $operation$)
\State \textbf{Send}($msg$, $currentLeader$)
\State \Return
\EndIf
\State $paxosInstance \leftarrow$ new PaxosInstance($opId$, $1$, $membership$, $REGULAR$)
\State $paxosInstance.proposedValue \leftarrow$ new ProposedValue($REGULAR$, $null$, $operation$)
\State $listOfProposes[opId] \leftarrow paxosInstance$
\If{$currentLeader = null$}  \LineComment{Need full Paxos round if no leader}
\State $msg \leftarrow$ new PrepareMessage($paxosInstance.id$, $paxosInstance.ballot$, $opId$, $REGULAR$)
\Else \LineComment{Skip prepare phase if leader exists}
\State $msg \leftarrow$ new AcceptMessage($paxosInstance.id$, $paxosInstance.ballot$, $opId$)
\EndIf
\ForAll{$p \in membership \wedge p \neq self$}
\State \textbf{Send}($msg$, $p$)
\EndFor
\State

\State \textbf{Upon Receive}(PrepareMessage, $sender$) \textbf{do:}
\State $paxosInstance \leftarrow listOfProposes[msg.operationId]$
\If{$paxosInstance = null$}
\State $type \leftarrow$ msg.type = JOIN ? JOIN : REGULAR
\State $paxosInstance \leftarrow$ new PaxosInstance($msg.id$, $msg.ballot$, $membership$, $type$)
\State $listOfProposes[msg.operationId] \leftarrow paxosInstance$
\EndIf
\If{$msg.ballot \geq paxosInstance.ballot$}
\State $paxosInstance.ballot \leftarrow msg.ballot$
\State $paxosInstance.promises[sender] \leftarrow true$
\State $promise \leftarrow$ new PromiseMessage($paxosInstance.id$, $msg.ballot$, $msg.operationId$, $msg.type$)
\State \textbf{Send}($promise$, $sender$)
\EndIf
\State

\State \textbf{Upon Receive}(PromiseMessage, $sender$) \textbf{do:}
\If{$\neg isLeader$}
\State \Return
\EndIf
\State $paxosInstance \leftarrow listOfProposes[msg.operationId]$
\State $paxosInstance.promises[sender] \leftarrow true$
\If{hasQuorum($paxosInstance.promises$)}
\State $accept \leftarrow$ new AcceptMessage($paxosInstance.id$, $paxosInstance.ballot$, $msg.operationId$)
\ForAll{$p \in membership \wedge p \neq self$}
\State \textbf{Send}($accept$, $p$)
\EndFor
\EndIf
\State

\State \textbf{Upon Receive}(AcceptMessage, $sender$) \textbf{do:}
\State $paxosInstance \leftarrow listOfProposes[msg.operationId]$
\If{$msg.ballot \geq paxosInstance.ballot$}
\State $paxosInstance.ballot \leftarrow msg.ballot$
\State $paxosInstance.accepts[sender] \leftarrow true$
\State $learn \leftarrow$ new LearnMessage($paxosInstance.id$, $msg.ballot$, $msg.operationId$)
\State \textbf{Send}($learn$, $currentLeader$)
\EndIf
\State

\State \textbf{Upon Receive}(LearnMessage, $sender$) \textbf{do:}
\State $paxosInstance \leftarrow listOfProposes[msg.operationId]$
\If{$paxosInstance = null \vee msg.ballot < paxosInstance.ballot$}
\State \Return
\EndIf
\State $proposedValue \leftarrow paxosInstance.proposedValue$
\State $paxosInstance.accepts[sender] \leftarrow true$
\If{hasQuorum($paxosInstance.accepts$)}
\If{$proposedValue.type = LEADER\_ELECTION$}
\State $newLeader \leftarrow proposedValue.host$
\State $currentLeader \leftarrow newLeader$
\State $isLeader \leftarrow newLeader = self$
\State \textbf{Trigger} leaderDecidedNotification($msg.operationId$, $newLeader$)
\EndIf
\State $listOfProposes \leftarrow listOfProposes \setminus \{msg.operationId\}$
\If{$isLeader$}
\State $decidedMessages[msg.operationId] \leftarrow msg$
\State $payload \leftarrow proposedValue \neq null$ ? $proposedValue.value$ : $null$
\ForAll{$p \in membership$}
\State $decided \leftarrow$ new DecidedMessage($msg.operationId$, $membership$, $payload$)
\State \textbf{Send}($decided$, $p$)
\EndFor
\EndIf
\EndIf
\end{algorithmic}
\end{algorithm}

\State $currentLeader \leftarrow \bot$
\State $electionId \leftarrow$ generateUUID()
\State $ballot \leftarrow$ generateNewBallot()
\State $paxosInstance \leftarrow$ new PaxosInstance($electionId$, $ballot$, $membership$, $LEADER\_ELECTION$)
\State $paxosInstance.proposedValue \leftarrow$ new ProposedValue($LEADER\_ELECTION$, $self$, $null$)
\State $msg \leftarrow$ new PrepareMessage($electionId$, $ballot$, $electionId$, $LEADER\_ELECTION$)
\ForAll{$p \in membership$}
\State \textbf{Send}($msg$, $p$)
\EndFor
\end{algorithmic}
\end{algorithm}

\begin{algorithm}
\caption{State Machine Protocol}
\begin{algorithmic}
\State \textbf{State:}
\State \hspace{1em} $self$ {current node identity}
\State \hspace{1em} $membership$ {list of current members}
\State \hspace{1em} $currentLeader$ {current leader node}
\State \hspace{1em} $isLeader$ {boolean indicating if this node is leader}
\State \hspace{1em} $ready$ {boolean indicating readiness to process operations}
\State \hspace{1em} $nextInstance$ {next instance number for operations}
\State \hspace{1em} $decided$ {set of decided operations}
\State \hspace{1em} $appState$ {application state - key-value map}
\State

\State \textbf{Upon orderRequest}($opId$, $operation$) \textbf{do:}
\If{$\neg ready$}
\State \Return
\EndIf
\If{$opId \in decided$}
\State \Return
\EndIf
\If{$\neg isLeader$}
\State $msg \leftarrow$ new OperationMessage($opId$, $self$, $nextInstance$, $operation$)
\State \textbf{Send}($msg$, $currentLeader$)
\State \Return
\EndIf
\State $proposeRequest \leftarrow$ new ProposeRequest($nextInstance$, $opId$, $operation$)
\State $nextInstance \leftarrow nextInstance + 1$
\State \textbf{Trigger} proposeRequest
\State

\State \textbf{Upon nodeDecidedNotification}($opId$, $type$, $node$) \textbf{do:}
\If{$node \in membership$}
\State \Return
\EndIf
\State $membership \leftarrow membership \cup \{node\}$
\If{$isLeader$}
\State $stateTransfer \leftarrow$ new StateTransferMessage($appState$, $membership$)
\State \textbf{Send}($stateTransfer$, $node$)
\EndIf
\State

\State \textbf{Upon decisionNotification}($opId$, $decision$, $membership$, $payload$) \textbf{do:}
\If{$opId \in decided$}
\State \Return
\EndIf
\If{$decision = COMMIT$}
\State $nextInstance \leftarrow nextInstance + 1$
\State $decided \leftarrow decided \cup \{opId\}$
\If{$payload \neq null$}
\State \Call{ExecuteOperation}{$opId$, $payload$}
\EndIf
\EndIf
\State

\State \textbf{Upon leaderDecidedNotification}($opId$, $newLeader$) \textbf{do:}
\State $currentLeader \leftarrow newLeader$
\State $isLeader \leftarrow newLeader = self$
\If{$isLeader$}
\State $ready \leftarrow true$
\Else
\State \textbf{Open Connection}($currentLeader$)
\EndIf

\end{algorithmic}
\end{algorithm}
